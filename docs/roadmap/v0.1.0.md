# paperwars.io: Version 0.1.0 Development Plan

**Development stage:** Public alpha
**Release type:** First public release (testing period and fixes only)
**Release theme:** Staged Testing, Measurement, Fixes and the First Public Launch
**Builds on:** [v0.0.20](v0.0.20.md) (Release candidate)
**Followed by:** 0.1.x improvement releases, then 0.2.0

Part of the [roadmap to v0.1.0](README.md).

---

## Overview

Versions 0.0.10 to 0.0.20 build everything paperwars.io needs to be a public game: persistence and a private alpha, final art and controller support, a rebuilt HUD, audio, menus and branding, a deeper economy, advanced multiplayer, larger worlds, customization and social systems, public accounts and infrastructure, and finally a release candidate with features frozen.

Version 0.1.0 adds no new features. It is a testing period followed by the first public release. Its content is whatever fixes and balance changes the testing period shows are needed.

The release has five central objectives:

1. Test the release candidate in widening rounds, from the developer and one friend up to a larger closed test.
2. Measure the game against the success criteria in GDD §18, plus performance, server load, economy health and retention.
3. Triage and fix bugs using clear severity rules, and make balance changes based on data.
4. Launch publicly with a release checklist, a rollback plan and monitoring.
5. Establish how versions are numbered and released from here on.

**Feature freeze holds throughout.** Any idea for a new feature found during testing goes into the backlog for a 0.1.x or 0.x.0 release.

---

## 1. Versioning From v0.1.0

**Priority:** High
**Goal:** Give every future release a clear meaning.

| Version | Meaning | Examples |
|---|---|---|
| 0.1.x | Small improvements and fixes | Balance tweaks, bug fixes, quality-of-life changes, small content additions, localisation |
| 0.x.0 | Major versions | New systems or big content: enabling the cosmetic shop (possibly 0.2.0), new environments, ranked play, new aircraft families |
| 1.0.0 | First full version | The complete game as described in the GDD, out of alpha and beta |

- Every release has a changelog entry and player-facing patch notes (v0.0.20 tooling).
- Client and server versions stay compatible within a release; the version check from v0.0.19 prevents mismatches.
- Database migrations are versioned and tested on a copy of production before each release.
- The GDD roadmap (§17) and `docs/roadmap/` are updated when the plan beyond v0.1.0 is decided.

## 2. Staged Testing Rounds

**Priority:** Critical
**Goal:** Find problems while the number of affected players is still small.

### A. Rounds

| Round | Players | Duration (provisional) | Focus |
|---|---|---|---|
| 1. Developer and friend | 2 | 1 week | Full feature pass, persistence acceptance test on production, controller vs keyboard |
| 2. Small invited group | About 10 | 1 to 2 weeks | Full campaign, multiplayer fairness, onboarding with people new to the game |
| 3. Larger closed test | 50 to 200 | 2 to 3 weeks | Several worlds, matchmaking, load, moderation, retention, browser variety |
| 4. Public launch | Open | Ongoing | Monitoring, fixes, 0.1.x releases |

### B. Entry and exit criteria

Each round starts only when the previous round's exit criteria are met:

- No open blocker bugs.
- No open critical bugs without an accepted workaround.
- Server stability targets met for the round's length.
- Key measurements recorded (section 3).
- The developer has approved moving on.

### C. Running a round

- Each round runs at least one full campaign (compressed campaigns allowed in round 1).
- Testers are given a short brief: what to try, how to report bugs (in-game report from v0.0.20), and the community channel.
- A summary is written at the end of each round: what was found, what was fixed, what was measured, what remains.

### D. Testers' data

- Test accounts follow the same privacy policy and terms as public accounts.
- Whether test progress carries into the public launch is decided and announced before round 3 (a campaign reset at launch is the default).

## 3. Measurements

**Priority:** Critical
**Goal:** Decide whether the game is ready based on evidence.

### A. GDD §18 success criteria

| Criterion | How it is measured |
|---|---|
| 1. A newcomer can join and fly within about one minute | Time from page load to first take-off (analytics) |
| 2. Players understand how to earn and spend paper | First mission completed and first aircraft bought without help; survey |
| 3. Different aircraft lead to meaningful decisions | Aircraft pick rates by mission type; no single dominant pick |
| 4. Bombing gives the defender a fair chance to respond | Share of raids where the defender was warned in time; defense success rate; survey |
| 5. Rewards create choices rather than grinding | Variety of missions chosen; session survey |
| 6. Defeat does not prevent further play | Return rate after losing a plane or a raid |
| 7. Activities exist at low population | Session length in worlds with few players |
| 8. Veterans are challenged without dominating newcomers | Newcomer retention in mixed worlds; strength spread in campaigns |
| 9. Players return voluntarily | Day 1, day 7 and day 30 retention |
| 10. The game remains understandable and fun | Survey, feedback log themes |

Targets for each are agreed with the developer before round 3.

### B. Performance

- Client frame rate and frame-time stability on the low-end target and typical hardware.
- Load time (first load and cached).
- Memory over a one-hour session.
- Network latency and reconnect frequency.

### C. Server load

- Concurrent players and worlds per server process.
- Tick time, message rate, CPU, memory, database latency.
- Comparison with the v0.0.19 load-test predictions.

### D. Economy health

- Resource sources and sinks per campaign day.
- Wealth distribution across players in each world.
- Raid outcomes, losses and recovery times.
- Detection of runaway leaders or players stuck without resources.

### E. Retention and engagement

- Return visits, session length, sessions per day.
- Drop-off points in the first session.
- Campaign completion rates.

## 4. Bug Triage and Severity

**Priority:** Critical
**Goal:** Fix the right things first, consistently.

### A. Severity scale

| Severity | Definition | Examples | Release rule |
|---|---|---|---|
| Blocker | Prevents playing, loses progress, or creates a security or legal problem | Cannot join; data loss on restart; account takeover; duplicated rewards at scale | Must be fixed before any round continues or the launch |
| Critical | Breaks a core feature or fairness for many players | Raids never end; defenses do not fire; a browser in the matrix cannot play | Must be fixed before launch |
| Major | Significant problem with a workaround | Mission occasionally fails to complete; controller loses focus in one menu | Fix before launch where possible; otherwise in the first 0.1.x |
| Minor | Small issue that does not affect play much | Visual glitch, text error, rare sound issue | Scheduled for 0.1.x |
| Trivial | Cosmetic or very rare | Slight misalignment | Backlog |

### B. Process

- Every report is reproduced, given a severity and linked to duplicates.
- Each fix includes a test where practical.
- Fixes go to staging first, are verified, then deployed.
- The developer reviews the open blocker and critical list at least twice a week during testing.

### C. Exploits

- Exploits that create resources, items or unfair advantages are treated as at least critical.
- Their effects are corrected through the ledger and admin tools from v0.0.18 and v0.0.19, with an audit trail.

## 5. Balance Changes

**Priority:** High
**Goal:** Adjust numbers, not systems.

### A. Allowed

- Aircraft statistics and costs.
- Mission rewards and difficulty tiers.
- Production rates, storage caps and protected reserves.
- Raid losses, cooldowns, protection times and the rules in `PVP` (`src/config.ts`).
- Defense statistics and costs.
- Campaign and inactivity durations.
- Bounty values and AI escort limits.

### B. Not allowed

- New mechanics, new resources, new aircraft, new mission types or new buildings.

### C. Process

- Each balance change is based on a measurement or a clear pattern in feedback.
- Changes are recorded in patch notes with the reason.
- Large changes are applied at a campaign reset, not mid-campaign, unless they fix an exploit.

## 6. Release Checklist

**Priority:** Critical
**Goal:** Launch deliberately, not accidentally.

Before public launch, confirm:

- [ ] All rounds completed with exit criteria met.
- [ ] Zero open blocker and critical bugs.
- [ ] Success-criteria targets met, or shortfalls accepted by the developer in writing.
- [ ] Load capacity covers the expected launch audience with margin.
- [ ] Backups verified with a fresh restore drill.
- [ ] Monitoring and alerts verified.
- [ ] Privacy policy, terms of service and FAQ published and current.
- [ ] Moderation tools tested; the developer (and any helpers) ready to moderate.
- [ ] Cosmetic shop flag confirmed off in production.
- [ ] Patch notes and launch announcement prepared.
- [ ] Rollback plan rehearsed on staging.
- [ ] Version tagged and changelog updated.

---

## 7. Launch and Rollback Plan

**Priority:** Critical
**Goal:** Be able to undo a bad launch quickly.

### A. Launch steps

1. Tag the release and deploy to staging; run the smoke test.
2. Announce a maintenance window if testers are online.
3. Deploy server, client and migrations to production.
4. Run the production smoke test: sign in, matchmaking, join, fly, mission, raid, reconnect.
5. Open public access (remove the invite restriction).
6. Announce the launch.

### B. Rollback triggers

- A blocker affecting many players that cannot be fixed within a short window.
- Data corruption or loss.
- Server instability beyond agreed limits.

### C. Rollback steps

- Restore the previous client and server version.
- Roll back migrations or restore the database from the last verified backup, depending on the problem.
- Re-enable the invite restriction if needed.
- Inform players through the news panel and community channel.
- Compensate affected players where appropriate (cosmetics only, never resources that break the economy).

---

## 8. Post-Launch Monitoring

**Priority:** Critical
**Goal:** Catch problems in the first days, when they matter most.

### A. First 72 hours

- The developer watches dashboards and alerts closely.
- Daily triage of reports and crash data.
- Hotfixes as 0.1.1, 0.1.2 and so on when needed.

### B. First campaign

- Track economy health and fairness through the first full public campaign.
- Review success-criteria measurements at its end.

### C. First month

- Retention review (day 1, day 7, day 30).
- Decide the content of the first 0.1.x improvement releases.
- Start planning the next major version. Enabling the cosmetic shop is considered only if retention meets the agreed target (GDD §14).

---

## 9. Testing and Verification

- Every round produces a written summary with measurements.
- Every fix is verified on staging before production.
- The persistence acceptance test from v0.0.10 is repeated before launch.
- The full browser matrix from v0.0.20 is repeated before launch.
- A restore drill and a rollback rehearsal are completed before launch.

## 10. Release Scope and Boundaries

| Deferred item | Owning version |
|---|---|
| Enabling the cosmetic shop | 0.2.0 or later, only after retention is proven |
| New aircraft, environments, mission types or resources | 0.x.0 major versions |
| Ranked or competitive ladders | 0.x.0 |
| Localisation | 0.1.x |
| Mobile and touch support | 0.x.0 |
| Free-text chat | Not before 1.0.0 |
| Full game as described in the GDD | 1.0.0 |

---

## 11. Developer Responsibilities

- Recruit testers for rounds 2 and 3.
- Approve entry and exit of every round.
- Agree success-criteria targets before round 3.
- Review the blocker and critical list regularly.
- Approve balance changes.
- Make the launch decision and perform or approve the launch steps.
- Moderate and communicate with players at launch.

## 12. AI Agent Implementation Strategy

| Phase | Focus |
|---|---|
| 1 | Prepare round 1: deploy the release candidate, set up dashboards, test briefs and summary templates |
| 2 | Round 1: developer and friend; fix blockers and critical bugs |
| 3 | Prepare round 2: onboarding checks, compressed and full campaign settings |
| 4 | Round 2: small invited group; fixes and first balance pass |
| 5 | Prepare round 3: capacity check, moderation readiness, success-criteria targets |
| 6 | Round 3: larger closed test; fixes, balance, performance |
| 7 | Release checklist, restore drill and rollback rehearsal |
| 8 | Public launch |
| 9 | Post-launch monitoring and hotfixes |
| 10 | First-month review and plan for 0.1.x and the next major version |

- The agent fixes bugs, implements balance changes, runs the automated and load tests, analyses the data and writes the round summaries.
- No new features. Proposals found during testing go into the backlog.
- Do not mark a round complete because the build compiles; use the exit criteria.
- Preserve every working feature from earlier versions.

---

## 13. Definition of Done

- [ ] All three test rounds completed with their exit criteria met.
- [ ] GDD §18 success criteria measured and targets met or accepted.
- [ ] Performance, server load, economy and retention measured and recorded.
- [ ] Zero open blocker and critical bugs.
- [ ] Balance changes applied and documented in patch notes.
- [ ] Release checklist completed.
- [ ] Rollback plan rehearsed.
- [ ] Public launch completed.
- [ ] Post-launch monitoring running.
- [ ] Versioning rules from section 1 adopted in the README and GDD.

---

## Final design principle

Version 0.1.0 is the moment paperwars.io stops being something the developer shows people and becomes something people choose to play. It should launch only when the evidence says it is fun, fair and reliable, and it should ship with the ability to listen, fix and roll back quickly when real players find what testing missed.
