# paperwars.io: Version 0.0.20 Development Plan

**Development stage:** Closed alpha, release candidate
**Release type:** Release candidate and feature freeze
**Release theme:** LiveOps, Shop Groundwork, Onboarding Retune, Compatibility and Support
**Builds on:** [v0.0.19](v0.0.19.md) (Public readiness)
**Followed by:** [v0.1.0](v0.1.0.md) (Testing period and first public release)

Part of the [roadmap to v0.1.0](README.md).

---

## Overview

Version 0.0.19 gives paperwars.io accounts, matchmaking, campaigns, moderation, analytics and production infrastructure. Technically, the game could open to the public.

Version 0.0.20 is the last version before the testing period that leads to v0.1.0. It is the release candidate. Its job is not to add another major system, but to make sure the game can be run, updated, supported and kept interesting once it is public, and that it works on the computers and browsers real players use.

After v0.0.20 is complete, features are frozen. Only fixes and balance changes go into the testing period.

The release has six central objectives:

1. Add LiveOps tools: scheduled events, an in-game news panel and patch notes.
2. Build the cosmetic shop infrastructure behind a disabled feature flag, so it can be turned on later without a rebuild (GDD §14: monetisation only after retention is validated).
3. Retune the tutorial and first-session experience using the data and feedback gathered since v0.0.10.
4. Verify and fix compatibility across Chrome, Edge, Firefox and Safari, and meet a defined low-end laptop target.
5. Provide player support: an in-game bug report, an FAQ and a community channel.
6. Freeze features and reach zero known release-blocking bugs.

The release must preserve every system from earlier versions. Do not redesign the HUD, menus or audio again. Do not add new aircraft, missions, territories or resources.

## 1. LiveOps Tools

**Priority:** High
**Goal:** Let the developer keep the game fresh and communicate with players without shipping a new build.

### A. Scheduled events

- Events are defined as data: name, description, start and end time, affected worlds or regions, rule modifiers, and rewards.
- Supported modifiers reuse existing systems only, for example:

| Event type | Uses |
|---|---|
| Double mission rewards for a mission category | Mission rewards (v0.0.6, v0.0.15) |
| Convoy weekend | World events (v0.0.15) |
| Bounty frenzy | Bounties (v0.0.16) |
| Aircraft spotlight | Mastery progress bonus for one aircraft |
| Cosmetic event | Time-limited earned cosmetics (v0.0.18) |

- Events are validated before they go live: no modifier may break the economy caps or anti-ruin rules (GDD §4.5).
- Events can be cancelled at any time; rewards already earned are kept.

### B. Event administration

- The admin console from v0.0.19 gets an events page: create, schedule, preview on staging, publish, cancel.
- Every change is recorded in the audit log.

### C. In-game news panel

- A small panel in the main menu and lobby (built with the v0.0.12 design system) showing news, active and upcoming events, and maintenance notices.
- Content is fetched from the server and cached; the game works without it.
- Short text only, consistent with the GDD §15 UI principles.

### D. Patch notes

- Every release has player-facing patch notes, written from the changelog.
- After an update, players see a short "What changed" card once, with a link to the full notes.

### E. Maintenance windows

- The developer can schedule maintenance: players are warned in advance, new world joins stop, worlds are saved and drained cleanly (v0.0.19 runbooks).

## 2. Cosmetic Shop Infrastructure (Disabled)

**Priority:** High
**Goal:** Build everything needed to sell cosmetics later, but keep it switched off until retention has been proven after v0.1.0.

### A. Feature flag

- A server-controlled flag `shop.enabled`, off in every environment except staging and local.
- When off, no shop UI is shown, no shop endpoints accept requests, and no payment provider code is loaded in the client.
- A test verifies that the production build with the flag off exposes no purchase path.

### B. Catalogue and pricing data

- Extend the cosmetic catalogue from v0.0.18 with optional prices, bundles and availability windows.
- Purchasable items are a separate set from earned items. Earned items are never sold, so earning stays meaningful.

### C. Purchase flow (staging only)

- Integration with one payment provider (to be chosen by the developer) in test mode.
- Server-side receipt validation; the client never grants items.
- Purchases are recorded in the inventory ledger from v0.0.18 with source `purchase` and a receipt reference, idempotently.
- Refunds and chargebacks remove the item and are logged.

### D. Rules that never change

From GDD §14, purchases must never increase:

- Aircraft performance, damage, ammunition or durability.
- Resource production or storage.
- Defensive effectiveness.
- Mission rewards or progression speed.

These rules are written as automated tests that run whether the shop is on or off.

### E. Compliance preparation

- Document what is needed before switching on: tax and VAT handling, prices by region, consumer rights and refunds, age rules, terms of sale.
- Do not switch on in this version or in v0.1.0.

## 3. Tutorial and Onboarding Retune

**Priority:** Critical
**Goal:** Make the first session work for strangers, using evidence instead of guesses.

### A. Inputs

- Funnel and retention data from v0.0.19 analytics (where players drop off).
- Feedback log entries from v0.0.10 onwards.
- Observations from invited playtests.

### B. Targets (GDD §18)

- A newcomer can join and begin flying within about one minute.
- The player understands how to earn and spend paper without extensive instructions.
- Defeat does not prevent further play.

### C. Changes allowed

- Reorder, shorten or remove tutorial steps.
- Improve first-time tips and key hints (GDD §15.8).
- Adjust the first missions the director offers to new players.
- Adjust new-player protection timing.
- Do not add new tutorial systems or new UI frameworks.

### D. Verification

- Fresh-account playtests with people who have never seen the game, on keyboard and on controller.
- Measure time to first flight, first mission completed, and first return visit.

## 4. Browser and Hardware Compatibility

**Priority:** Critical
**Goal:** Make sure the game works on the computers and browsers players actually use.

### A. Browser matrix

| Browser | Platforms | Requirement |
|---|---|---|
| Chrome | Windows, macOS, Linux | Fully supported |
| Edge | Windows | Fully supported |
| Firefox | Windows, macOS, Linux | Fully supported |
| Safari | macOS | Fully supported, including audio unlock and gamepad behaviour |

- Each is tested for: loading, sign-in, matchmaking, flight, combat, base management, audio, controller, reconnect.
- Known browser differences (WebGL extensions, gamepad mappings, audio autoplay, storage limits) are handled or documented.
- Unsupported browsers see a clear message, not a broken page.

### B. Low-end laptop target

- Define a minimum specification with the developer, for example a laptop with integrated graphics from about five years ago.
- On that machine at the Low preset (v0.0.8 graphics settings): a stable frame rate target, a load-time target and no memory growth over a one-hour session.
- Performance fixes are allowed: asset budgets, level of detail, draw-call reductions, effect limits.

### C. Network conditions

- Test with higher latency and packet loss, building on the `LATENCY` option and load tests from v0.0.9.
- The game remains playable and reconnects cleanly.

### D. Results

- Publish the matrix and measurements in the README.

## 5. Player Support

**Priority:** High
**Goal:** Give public players a way to get help and report problems.

### A. In-game bug report

- Evolves the feedback log from v0.0.10 into a player-facing report form in the pause menu.
- Automatically attaches build version, browser, world, recent errors and an optional screenshot.
- Players can describe the problem in a short text field; reports go to the admin console.
- Rate-limited.

### B. FAQ

- A short FAQ reachable from the main menu: controls, campaigns, offline protection, accounts, data deletion, reporting players.
- Written in plain language and kept consistent with the game.

### C. Community channel

- A community channel (for example Discord) chosen by the developer, linked from the menu.
- Basic rules and moderation in line with the terms of service.

### D. Support process

- A documented process for the developer: triage reports daily during the test period, link duplicates, reply to account issues.

## 6. Feature Freeze and Release Candidate Stabilization

**Priority:** Critical
**Goal:** End this version with a build that is ready for the testing period.

### A. Feature freeze

- After this version's features are merged, no new features until v0.1.0 ships.
- Allowed afterwards: bug fixes, balance changes, performance fixes, text corrections, compatibility fixes.

### B. Bug triage

- Every open issue is triaged with the severity scale defined in [v0.1.0](v0.1.0.md).
- All blocker and critical issues are fixed before v0.0.20 is declared complete.

### C. Full regression

- All automated tests pass.
- Full manual regression: single player, multiplayer, persistence, campaigns, controller, all browsers in the matrix.
- The v0.0.10 persistence acceptance test is repeated on production infrastructure.

### D. Release candidate build

- A tagged release candidate build deployed to staging and then production, with accounts limited to invited testers until the v0.1.0 test rounds begin.

## 7. Testing and Verification

- LiveOps: scheduled event start and end, cancellation, rule validation, news and patch notes display.
- Shop: flag off hides everything in production; flag on in staging completes test purchases, refunds and idempotent grants; performance-neutrality tests pass.
- Onboarding: time-to-first-flight and first-mission metrics measured with new players.
- Compatibility: full matrix completed and recorded.
- Support: reports arrive in the admin console with the right context.
- Full regression and persistence acceptance test on production.

## 8. Release Scope and Boundaries

| Deferred item | Owning version |
|---|---|
| Enabling the cosmetic shop | 0.2.0 or later, after retention is proven |
| New aircraft, missions, territories or environments | 0.x.0 major versions after v0.1.0 |
| Ranked play | After v0.1.0 |
| Mobile and touch | After v0.1.0 |
| Free-text chat | Not before 1.0.0 |
| Localisation beyond English | 0.1.x or later (strings are already in one dictionary since v0.0.12) |

## 9. Developer Responsibilities

- Choose the payment provider (for test mode) and the community channel.
- Define the minimum laptop specification and provide or borrow test hardware.
- Provide access to a macOS machine for Safari testing.
- Recruit first-time players for onboarding tests.
- Write or approve FAQ, patch notes and news content.
- Approve the feature freeze and the release candidate.

## 10. AI Agent Implementation Strategy

| Phase | Focus |
|---|---|
| 1 | Audit v0.0.19, triage all open issues, set the regression baseline |
| 2 | Scheduled events and the admin events page |
| 3 | News panel, patch notes and maintenance windows |
| 4 | Shop infrastructure behind the feature flag, with performance-neutrality tests |
| 5 | Onboarding retune from data and new-player tests |
| 6 | Browser matrix testing and fixes |
| 7 | Low-end laptop performance work |
| 8 | In-game bug report, FAQ and support process |
| 9 | Feature freeze, full regression and blocker fixes |
| 10 | Release candidate build, persistence acceptance test on production, sign-off |

- Work in reviewable increments with a developer checkpoint after LiveOps, after compatibility and before the freeze.
- Do not mark a phase complete because the code compiles; verify it in each browser and on the target hardware.
- Preserve all earlier features.

## 11. Definition of Done

- [ ] Scheduled events can be created, previewed, published and cancelled without a new build.
- [ ] The news panel, patch notes and maintenance notices work.
- [ ] Shop infrastructure works on staging and is fully hidden and inactive in production.
- [ ] Tests confirm that no purchasable item can affect gameplay.
- [ ] The tutorial and first session have been retuned and verified with new players.
- [ ] Chrome, Edge, Firefox and Safari pass the compatibility matrix.
- [ ] The low-end laptop target is met.
- [ ] In-game bug reports, FAQ and the community channel are live.
- [ ] Features are frozen.
- [ ] Zero known blocker or critical bugs.
- [ ] All automated tests and the full manual regression pass.
- [ ] The release candidate is deployed and ready for the v0.1.0 testing period.

---

## Final design principle

A release candidate is not the place for new ideas. It is the version where the game becomes something that can be run, updated, supported and trusted by people who have never met the developer. Everything that can be turned on later should be ready; nothing that could harm fairness should be on.
