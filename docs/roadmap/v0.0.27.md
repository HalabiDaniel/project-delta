# paperwars.io: Version 0.0.27 Development Plan

**Development stage:** Closed alpha (preparing for public access)
**Release type:** Operations milestone
**Release theme:** The Admin Dashboard: Running, Moderating and Supporting the Game From One Place
**Builds on:** [v0.0.26](v0.0.26.md) (public readiness: accounts, matchmaking, moderation backend, production infrastructure)
**Followed by:** [v0.0.28](v0.0.28.md) (release candidate)

Part of the [roadmap to v0.1.0](README.md).

---

## Overview

Until now the developer runs the game with a command-line tool (v0.0.10) and a minimal protected
admin endpoint (v0.0.14). v0.0.26 adds what strangers need: accounts, matchmaking, reports,
moderation actions, analytics and production infrastructure, all with server-side APIs but no
convenient way to use them.

Before the public launch, the developer needs **one complete admin dashboard**: a protected web
app to see the live game, find any player, act on reports, read feedback, investigate the
economy, run events and announcements, and check the infrastructure. It replaces the command line
for day-to-day operations (the command line stays for emergencies).

The release has six central objectives:

1. A secure admin app with roles, two-factor sign-in and an append-only audit log.
2. Live operations: sessions, players online, server health.
3. Player support: look up any player, their base, paper history, devices and sessions, and fix
   problems through audited actions.
4. Moderation: the report queue and every moderation action from v0.0.26.
5. Feedback and economy views.
6. LiveOps: scheduled events, the in-game news panel, patch notes and maintenance windows (moved
   here from the release candidate).

No new gameplay. The dashboard only reads what the server already records and calls actions the
server already implements, plus the LiveOps scheduler.

---

## 1. The Admin App

**Priority:** Critical

### A. Delivery

- A separate entry in the same Vite build (`admin.html`, served at `/admin` on the game's domain),
  built with the v0.0.15 design system, so it shares components and styling with the game.
- It talks only to an admin API on the game server (`/admin/api/...`), never to the database
  directly.
- Works on a laptop and a phone (for checking the game on the go).

### B. Security

- Sign-in with an admin account (v0.0.26 accounts) **plus two-factor authentication** (an
  authenticator app). The v0.0.14 `ADMIN_KEY` is retired except for emergency command-line use.
- Roles: **Owner** (everything, including roles and destructive actions), **Moderator** (reports,
  player moderation, read-only economy), **Support** (player lookup, feedback, pass reissue).
- Short sessions, CSRF protection, rate limits, and an optional IP allowlist.
- Destructive actions (bans, refunds, ending a session, restoring a backup) ask for a reason and a
  confirmation.

### C. Audit log

- Every action is recorded: who, when, what, the target, the reason, and the state before and
  after. Append-only and kept apart from game data.
- Searchable and exportable from the dashboard.

---

## 2. Overview Page

- Players online, sessions running and their fill, joins in the last hour.
- Server health per game server: tick time (average and worst), memory, error rate, database
  latency, version deployed.
- Alerts: the server down, error spikes, backup failures, unusual economy activity.
- Charts for the last 24 hours and 7 days (the analytics from v0.0.26).

---

## 3. Sessions

- Every running session: time left, players and desks (a live mini-map with each desk's state:
  player-held, draining, empty, open, AI-held), raids in progress, ping per player.
- Actions: send a message to a session, end it early with notice, close it to new players, free a
  stuck desk, remove a player from a session.
- Ended sessions: results and a short timeline (joins, raids, settlements, errors), for support.

---

## 4. Players

- Search by username, account email, player id or public id.
- A player's page:
  - account and sign-in methods, guest or signed in, devices (device tokens) with last use;
  - the base (buildings, levels, damage, hangar and planes), paper balance and **transaction
    history** with the reason for every change;
  - sessions played, statistics, reports filed by and about them, moderation history.
- Actions: rename (with reason), reissue a pass (a transfer code), log out every device, kick,
  mute emotes, temporary or permanent ban, restore a wrongly destroyed plane or building, a paper
  correction. Corrections go through the ledger with their own idempotency key and reason, so the
  history stays complete.

---

## 5. Moderation

- The report queue from v0.0.26: filter by reason, status (open, actioned, dismissed) and age;
  grouped duplicates; the automatic context (session, time, recent encounters).
- Act from the report: warn, rename, mute, kick, ban, dismiss, each recorded.
- Flags from abuse detection (v0.0.26: multiple accounts, reward farming, suspicious patterns) with
  the evidence that raised them.
- The name and banner block list, editable.

---

## 6. Feedback

- The playtest feedback log from v0.0.14, and later the in-game support reports from v0.0.28.
- Filter by category, rating, version and date; mark as new, triaged, fixed or won't fix; link to
  an issue.
- Export to CSV or Markdown.

---

## 7. Economy

- Paper earned and spent per hour and per source (missions, raids, production, bounties, events),
  from the ledger.
- The richest and fastest-growing players, and anyone whose income looks unusual.
- Aircraft folded and lost per type; buildings built and destroyed.
- Read-only for Moderators; corrections only through a player's page (section 4).

---

## 8. LiveOps

Moved here from the release candidate plan.

### A. Scheduled events

- Events are data: name, description, start and end, which sessions or regions, rule modifiers and
  rewards. Modifiers reuse existing systems only:

| Event type | Uses |
|---|---|
| Double rewards for a mission category | Mission rewards (v0.0.6, v0.0.18) |
| Convoy weekend | World events (v0.0.18) |
| Bounty frenzy | Bounties (v0.0.19) |
| Aircraft spotlight | Mastery bonus for one aircraft |
| Cosmetic event | Time-limited earned cosmetics (v0.0.23) |

- Validated before they go live: no modifier may break the economy caps or anti-ruin rules
  (GDD §4.5). Previewed on staging (v0.0.26), published, cancelled at any time (rewards already
  earned are kept).

### B. News, patch notes and maintenance

- An in-game news panel (main menu and lobby) with news, active and upcoming events and maintenance
  notices, written in the dashboard; the game works without it.
- Patch notes per release, and a "What changed" card shown once after an update.
- Maintenance windows: players warned in advance, new joins stop, sessions end cleanly, then the
  deploy runs.

---

## 9. Infrastructure

- Deploys: which version runs where, with a link to its notes.
- Backups: the list of daily backups, their size and status, a "back up now" button, and a guided
  restore into staging (restoring production is Owner-only, with two confirmations).
- Links to the host's logs and metrics.

---

## 10. Testing and Verification

- Every admin API endpoint refuses requests without the right role (tested for every endpoint).
- Every action writes exactly one audit entry with before and after state.
- Paper corrections go through the ledger and are idempotent.
- Two-factor sign-in, session expiry and rate limits are tested.
- Browser tests of every page on desktop and phone widths.
- A security review of the admin app and API before the version is done.

---

## 11. Release Scope and Boundaries

- No new gameplay and no new player-facing features apart from the news panel and patch notes.
- The cosmetic shop's admin pages come with the shop itself (disabled) in v0.0.28.

---

## 12. Developer Responsibilities

- Choose who gets which role (at first, only the developer as Owner).
- Set up two-factor authentication.
- Use the dashboard for a week of the closed alpha and list what is missing.

## 14. Definition of Done

- [ ] The admin app is served at `/admin`, with two-factor sign-in and roles.
- [ ] Every action is in an append-only audit log with before and after state.
- [ ] The overview shows players, sessions and server health with alerts.
- [ ] Sessions can be inspected and managed live.
- [ ] Any player can be found; their base, paper history and devices are visible; support actions work.
- [ ] Reports and abuse flags can be worked through and acted on.
- [ ] Feedback can be triaged and exported; the economy can be investigated.
- [ ] Events, news, patch notes and maintenance windows are run from the dashboard.
- [ ] Backups can be checked and restored to staging from the dashboard.
- [ ] All tests pass and the security review is done.

---

## Final Design Principle

When strangers arrive, every question about the game ("is it up?", "where did my plane go?", "who
keeps griefing me?") must be answerable in a minute, from one place, and every answer that changes
something must leave a trace.
