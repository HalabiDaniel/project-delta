# paperwars.io: Version 0.0.14 Development Plan

**Development stage:** Private two-player alpha (online)
**Release type:** Deployment and operations milestone
**Release theme:** Going Live: the Whole Multiplayer System on the Internet, Backups, Feedback and the First Online Playtest
**Builds on:** [v0.0.13](v0.0.13.md) (sessions and the territory lifecycle)
**Followed by:** [v0.0.15](v0.0.15.md) (HUD and UI revamp)

Part of the [roadmap to v0.1.0](README.md).

---

## Overview

After v0.0.12 and v0.0.13 the multiplayer server is complete enough to run for real: persistent,
portable bases, timed sessions, fair disconnects, restore and crash recovery. This is the version
in which **the entire multiplayer system becomes active on the internet**, so the developer and a
friend can play from their own homes, on their own networks, without running anything locally.
Every later version is then tested online.

The setup is kept cheap, reliable and simple (decided 2026-11-02):

| Part | Where | Why |
|---|---|---|
| The game (the web page) | **Vercel**, as today | Already set up; fast and free for this use |
| The game server (Node + Colyseus) | **Railway** | Runs a long-lived server with WebSockets (Vercel can't: it doesn't keep connections open), restarts it automatically, deploys from GitHub |
| The database (PostgreSQL) | **Railway**, in the same project | One place to manage; the server reaches it privately |
| Daily backups | A scheduled job on Railway, copies to **Cloudflare R2** | Off-site copies that survive the project itself |

The hosting can move later (v0.0.22 adds production-scale infrastructure); everything is
configured through environment variables, so moving means changing settings, not code.

The release has seven central objectives:

1. Deployment: the server on Railway with HTTPS and secure WebSockets, the game on Vercel finding
   it automatically.
2. A simple, step-by-step setup guide for the developer (section 9), checked against the real
   services.
3. Invite-only access for the alpha, with a minimal protected admin endpoint (the full dashboard is
   v0.0.23).
4. Daily backups with a tested restore.
5. Logs and an uptime check.
6. The playtest feedback log (F8).
7. The first online playtest with the developer and a friend (v0.0.10's acceptance sequence), plus
   v0.0.11's remaining hardware checks.

## 1. Deployment

**Priority:** Critical

### A. The server on Railway

- A `Dockerfile` (or Railway's own builder) and a `railway.json` in the repository build and start
  the server (`npm run server`), so Railway deploys every push to `main` automatically.
- `GET /health` answers `200 OK` with the version, store status and session count; Railway uses it
  to decide whether a deploy is healthy and to restart the server if it stops answering.
- The server listens on Railway's `PORT`; Railway gives it a public HTTPS address, which also serves
  secure WebSockets (`wss://`).
- `ALLOWED_ORIGINS` lists the addresses the game is served from (the Vercel domain and any custom
  domain); connections from anywhere else are refused.
- Restart policy: always restart on failure.
- Graceful shutdown (v0.0.13) runs on every deploy, so a deploy never loses a confirmed change.

### B. The game on Vercel

- The game reads the server address from `VITE_SERVER_URL` at build time, so players never type
  `?server=`. `?server=` keeps working for testing.
- Multiplayer is reachable from the main menu without `?mp` in the address.
- Vercel serves the precompressed `.br` and `.gz` files with long-lived caching (a v0.0.11
  leftover), and licensed model files are delivered from the private location documented in
  `assets/licensed/README.md`, never committed (v0.0.11 leftover).

### C. Settings

| Variable | Where | Value |
|---|---|---|
| `DATABASE_URL` | Railway (server) | A reference to the Railway Postgres database |
| `TOKEN_PEPPER` | Railway (server) | A long random secret (generated in the guide) |
| `ACCESS` | Railway (server) | `invite` |
| `NODE_ENV` | Railway (server) | `production` |
| `ALLOWED_ORIGINS` | Railway (server) | The game's address(es) |
| `ADMIN_KEY` | Railway (server) | A long random secret for the admin endpoint |
| `VITE_SERVER_URL` | Vercel (game) | `wss://` + the Railway server address |
| `R2_*` | Railway (backup job) | Cloudflare R2 bucket name, endpoint and keys |

No secret is ever in the repository or the game's code.

## 2. Access and Administration for the Alpha

**Priority:** Very high

- `ACCESS=invite`: a first join needs an invite code or link (`…/?invite=CODE`). Players choose
  their username on that first join (v0.0.12).
- The command-line tool (`npm run admin`) works against the live database from the developer's
  computer (section 9, step 8): invites, players, revoke, reissue a pass.
- A **minimal protected admin endpoint** on the server (`/admin`, requires `ADMIN_KEY`), for what
  the command line can't do on a running server: list sessions and connected players with ping,
  kick a player, end a session with notice, free a desk stuck in the wrong state.
- Every admin action is logged. The complete admin dashboard is **v0.0.23**.

---

## 3. Backups

**Priority:** Critical

- A small scheduled job in the same Railway project runs `pg_dump` **every day**, compresses it and
  uploads it to a Cloudflare R2 bucket.
- Copies are kept for **14 days** (at least the plan's seven), older ones deleted by the job.
- `npm run db:restore -- <file>` restores a backup into a database (a fresh one for a drill, or the
  live one in an emergency), with a confirmation prompt.
- **Restore drill:** before this version is done, a backup is restored into a fresh database, the
  server is pointed at it, and a player's base and paper are checked to be intact. The result is
  recorded in the guide.

---

## 4. Logs and Monitoring

**Priority:** High

- The structured logs from v0.0.13 go to Railway's log viewer (searchable by session id and player
  id), and are kept for the alpha period.
- A free external uptime check (for example UptimeRobot) calls `/health` every few minutes and
  emails the developer if the server is down.
- Errors are logged with context; the same error repeating is logged once with a count.

---

## 5. Playtest Feedback Log

**Priority:** High

- Opened with **F8** or from the pause menu.
- Category: bug, gameplay frustration, confusing interface, performance problem, balance concern,
  missing feature, general enjoyment. Free text, optional steps to reproduce, an enjoyment rating
  (1 to 5).
- Attached automatically: version, player and session, position and mode, recent ping and frame
  rate, device and browser.
- Stored in the `feedback` table, rate limited, and exported as CSV or Markdown with
  `npm run admin -- feedback export`.

---

## 6. Testing at Scale

**Priority:** Critical

- Bots join and leave at random, drop their connection, and keep playing through a server restart
  (a graceful one and a killed process), never duplicating a base or a reward.
- The load test runs against a Railway deployment with saving on: two sessions of 16 bots.
- Measured and recorded in the README: server tick stability, database writes per second and their
  latency, reconnection time after a refresh and after a restart, server memory over a multi-hour
  run, and the monthly cost observed.

---

## 7. The First Online Playtest

**Priority:** Critical

Played on the deployed server, from two computers on two different networks (v0.0.10's mandatory
acceptance sequence, adapted to sessions and portable bases):

1. The developer joins a session and is placed on a desk.
2. The friend joins the same session and is placed on another desk.
3. Both build aircraft and buildings.
4. Both complete missions and earn paper.
5. Both fight in the air.
6. One player disconnects; the other keeps playing.
7. The disconnected player returns within the grace and is back on the same desk.
8. A raid is started on a player who then leaves: the raid finishes normally, then the desk empties.
9. Both leave.
10. The server is restarted (and, separately, the process is killed).
11. Both return in a new session, on new desks, with their bases, planes and paper as they left them.

Also in this playtest (left over from v0.0.11, they need real hardware):

- The controller checklist on a real Xbox or PlayStation controller.
- The performance budgets measured with `?perf` on both test computers.
- The second two-player playtest's blocking issues fixed.

The result, the date, the builds used and any deviations are recorded in the README.

## 9. Setup Guide for the Developer

This is the guide the developer follows once the code for this version has been merged. Each step
says what to click or type. Railway, Vercel and Cloudflare sometimes rename buttons; the agent
re-checks every step against the live services while building this version and updates the guide
(it also goes into `docs/SERVER_SETUP.md`).

**What you need:** your GitHub account (the repository is already there), your Vercel account (the
game is already on it), a card for Railway (the Hobby plan has a small monthly fee plus usage;
check the current price on railway.com), and about 45 minutes.

### Step 1: Create the Railway project

1. Go to railway.com and sign in **with GitHub**.
2. Click **New Project** → **Deploy from GitHub repo** → choose `HalabiDaniel/project-delta`.
   Allow Railway to access the repository if it asks.
3. Railway starts building straight away. The first build may fail because the settings aren't
   there yet; that's expected.

### Step 2: Add the database

1. In the project, click **New** (or **Create**) → **Database** → **PostgreSQL**.
2. Wait until it shows as running. That's your database; Railway backs it with a disk.

### Step 3: Make two secrets

On your computer, run this twice and keep both results somewhere safe (a password manager):

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

The first is your `TOKEN_PEPPER`, the second your `ADMIN_KEY`. **Never change the pepper later**:
changing it logs every player out.

### Step 4: Configure the server

1. Click the **server service** (the one named after the repository) → **Variables**.
2. Add each of these (**New Variable**, name and value):

| Name | Value |
|---|---|
| `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` (type it exactly; Railway fills in the database's private address) |
| `TOKEN_PEPPER` | your first secret |
| `ADMIN_KEY` | your second secret |
| `ACCESS` | `invite` |
| `NODE_ENV` | `production` |

3. Go to **Settings** → **Networking** → **Generate Domain**. Railway gives the server an address
   like `project-delta-production.up.railway.app`. Copy it.
4. Back in **Variables**, add `ALLOWED_ORIGINS` with your game's address, for example
   `https://project-delta.vercel.app` (several addresses separated by commas).
5. Railway redeploys. When it shows **Active**, open `https://<server address>/health` in your
   browser: you should see `ok` with the version. If not, open **Deployments** → the latest one →
   **Logs**; the server says what's missing.

### Step 5: Point the game at the server

1. Go to vercel.com → your project → **Settings** → **Environment Variables**.
2. Add `VITE_SERVER_URL` = `wss://<server address>` (the Railway address from step 4, starting with
   `wss://`), for **Production** (and **Preview** if you want preview builds to use it too).
3. Go to **Deployments** → the latest production deployment → **⋯** → **Redeploy**.
4. Open the game, go to **Multiplayer**: the lobby should list sessions (or say there are none yet)
   instead of "No server".

### Step 6: Set up backups

1. Go to dash.cloudflare.com (create a free account if needed) → **R2** → **Create bucket**, name it
   `paperwars-backups`.
2. In R2, **Manage API tokens** → **Create API token** with **Object Read & Write** on that bucket.
   Copy the **Access Key ID**, **Secret Access Key** and the **endpoint** URL it shows.
3. In Railway, the repository's backup job appears as its own service (`backup`). Click it →
   **Variables**, and add `DATABASE_URL` = `${{Postgres.DATABASE_URL}}`, `R2_BUCKET` =
   `paperwars-backups`, `R2_ENDPOINT`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`.
4. Its **Settings** → **Cron Schedule** is already set to once a day by the repository; click
   **Run now** (or wait a day) and check that a file appears in the R2 bucket.

### Step 7: Check that it's alive from outside

1. Go to uptimerobot.com (free), add an **HTTP monitor** for `https://<server address>/health`
   every 5 minutes, with your email for alerts.

### Step 8: Invite your friend

1. In Railway, click the **Postgres** service → **Variables** (or **Connect**) and copy
   `DATABASE_PUBLIC_URL`: the address your own computer uses to reach the database.
2. On your computer, in the project folder:

```bash
DATABASE_URL='<DATABASE_PUBLIC_URL>' TOKEN_PEPPER='<your pepper>' npm run admin -- invite create "for my friend"
```

3. It prints a code like `K7Q2M-9XRTA`. Send your friend the link
   `https://<your game address>/?invite=K7Q2M-9XRTA`. Make one for yourself the same way.
4. Each of you opens the link, chooses a username, and you're in.

### Step 9 (optional): Your own domain

If you own a domain: in Vercel, **Settings** → **Domains** → add `play.yourdomain.com`; in Railway,
the server's **Settings** → **Networking** → **Custom Domain** → add `server.yourdomain.com`. Each
shows a DNS record to add at your domain registrar. Then update `ALLOWED_ORIGINS` (step 4) and
`VITE_SERVER_URL` (step 5) to the new addresses.

### When something goes wrong

| What you see | What to check |
|---|---|
| "No server" in the lobby | `VITE_SERVER_URL` in Vercel (step 5) and that you redeployed; `/health` opens |
| `/health` doesn't open | Railway → server → Deployments → Logs; usually a missing variable |
| "Connection refused" or origin errors in the browser console | `ALLOWED_ORIGINS` contains exactly the game's address, with `https://` |
| Everyone was logged out | `TOKEN_PEPPER` changed; set it back to the original |
| No backup in R2 | Railway → backup → Logs; the R2 keys and endpoint |

## 12. Definition of Done

- [ ] The server runs on Railway over HTTPS and WSS, restarts on failure, and deploys from `main`.
- [ ] The game on Vercel finds the server without `?server=` and multiplayer is in the main menu.
- [ ] Access is invite-only; usernames are chosen on first join.
- [ ] The admin CLI works against the live database; the minimal admin endpoint is protected and logged.
- [ ] Daily backups run, are kept for 14 days, and a restore into a fresh database has been tested.
- [ ] Logs are searchable; the uptime check alerts the developer.
- [ ] The feedback log works and exports to CSV and Markdown.
- [ ] Bots and the load test pass against the deployment; measurements are recorded.
- [ ] The online acceptance sequence has passed with the developer and the friend.
- [ ] v0.0.11's controller and performance checks are done on real hardware.
- [ ] The setup guide is complete and was followed successfully by the developer.

## Final Design Principle

From this version on, paperwars.io lives on the internet. Two people in two homes open a link and
play together, and every later version is built and tested on that live system.
