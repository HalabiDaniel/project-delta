**Status (2026-11-06): live.** The developer followed [docs/SERVER_SETUP.md](../SERVER_SETUP.md):
the server and database run on Railway, the game on Vercel finds them, backups run nightly with
the drill, and UptimeRobot watches `/health`. The load test ran against the deployment. Left: the
online playtest with the friend (section 7) and v0.0.11's hardware checks.

- **Access is open, not invite-only** (the developer's decision, 2026-11-06): players open the
  game and choose a username, with no invite and no terminal. `ACCESS=invite` can be set again at
  any time; accounts with sign-in are v0.0.20.

Changes from the plan, for the developer to confirm:

- **No `railway.json`.** Railway deprecated its per-service config files (`railway.json` /
  `railway.toml`): new services can't use them, and they stop being read on 2026-12-01. Railway
  builds from the repository's `Dockerfile` on its own; the health check path, the restart policy
  and the backup job's cron schedule and start command are four settings in the dashboard, listed
  in the guide. (Railway's replacement, `.railway/railway.ts`, needs its command-line tool to
  apply; not worth it for two services.)
- **The restore drill runs every night**, not once: with a second database (`Drill`), the backup
  job restores each new backup into it and compares players, bases, buildings, planes and paper
  with the live database (`drill.done` in the logs). The plan's one-off drill is the first run.
- **Origins**: a request with no `Origin` header (bots, the load test, `curl`) is let through:
  the check keeps other websites from embedding the game; who may play is the invite's and the
  device token's job. `ALLOWED_ORIGINS` accepts `*` in a host name for Vercel's preview builds.
  Unset in production, the server warns and allows any origin rather than refusing to start
  (the guide sets it).
- **Kick** keeps the player out for 10 minutes by default (`--minutes`); revoking for good is
  still `npm run admin -- player revoke`.
- **Vercel** compresses files itself (it doesn't serve the `.br` / `.gz` files next to them), so
  `vercel.json` only sets the long-lived caching for the hashed files in `assets/`.

## Overview

After v0.0.12 and v0.0.13 the multiplayer server is complete enough to run for real: persistent,
portable bases, timed sessions, fair disconnects, restore and crash recovery. This is the version
in which **the entire multiplayer system becomes active on the internet**, so the developer and a
friend can play from their own homes, on their own networks, without running anything locally.
Every later version is then tested online.

The setup is kept cheap, reliable and simple (decided 2026-11-02):

| Part | Where | Why |
|---|---|---|
| The game (the web page) | **Vercel**, as today | Already set up; fast and free for this use |
| The game server (Node + Colyseus) | **Railway** | Runs a long-lived server with WebSockets (Vercel can't: it doesn't keep connections open), restarts it automatically, deploys from GitHub |
| The database (PostgreSQL) | **Railway**, in the same project | One place to manage; the server reaches it privately |
| Daily backups | A scheduled job on Railway, copies to **Cloudflare R2** | Off-site copies that survive the project itself |

The hosting can move later (v0.0.26 adds production-scale infrastructure); everything is
configured through environment variables, so moving means changing settings, not code.

The release has seven central objectives:

1. Deployment: the server on Railway with HTTPS and secure WebSockets, the game on Vercel finding
   it automatically.
2. A simple, step-by-step setup guide for the developer (section 9), checked against the real
   services.
3. Invite-only access for the alpha, with a minimal protected admin endpoint (the full dashboard is
   v0.0.27).
4. Daily backups with a tested restore.
5. Logs and an uptime check.
6. The playtest feedback log (F8).
7. The first online playtest with the developer and a friend (v0.0.10's acceptance sequence), plus
   v0.0.11's remaining hardware checks.

## 1. Deployment

**Priority:** Critical

### A. The server on Railway

- A `Dockerfile` in the repository builds and starts the server, so Railway deploys every push
  to `main` automatically. (Planned with a `railway.json`, which Railway has since deprecated; the
  few settings it held are set in the dashboard, see the guide.)
- `GET /health` answers `200 OK` with the version, store status and session count; Railway uses it
  to decide whether a deploy is healthy and to restart the server if it stops answering.
- The server listens on Railway's `PORT`; Railway gives it a public HTTPS address, which also serves
  secure WebSockets (`wss://`).
- `ALLOWED_ORIGINS` lists the addresses the game is served from (the Vercel domain and any custom
  domain); connections from anywhere else are refused.
- Restart policy: always restart on failure.
- Graceful shutdown (v0.0.13) runs on every deploy, so a deploy never loses a confirmed change.

### B. The game on Vercel

- The game reads the server address from `VITE_SERVER_URL` at build time, so players never type
  `?server=`. `?server=` keeps working for testing.
- Multiplayer is reachable from the main menu without `?mp` in the address.
- Vercel serves the precompressed `.br` and `.gz` files with long-lived caching (a v0.0.11
  leftover), and licensed model files are delivered from the private location documented in
  `assets/licensed/README.md`, never committed (v0.0.11 leftover).

### C. Settings

| Variable | Where | Value |
|---|---|---|
| `DATABASE_URL` | Railway (server) | A reference to the Railway Postgres database |
| `TOKEN_PEPPER` | Railway (server) | A long random secret (generated in the guide) |
| `ACCESS` | Railway (server) | `invite` |
| `NODE_ENV` | Railway (server) | `production` |
| `ALLOWED_ORIGINS` | Railway (server) | The game's address(es) |
| `ADMIN_KEY` | Railway (server) | A long random secret for the admin endpoint |
| `VITE_SERVER_URL` | Vercel (game) | `wss://` + the Railway server address |
| `R2_*` | Railway (backup job) | Cloudflare R2 bucket name, endpoint and keys |

No secret is ever in the repository or the game's code.

## 2. Access and Administration for the Alpha

**Priority:** Very high

- `ACCESS=invite`: a first join needs an invite code or link (`…/?invite=CODE`). Players choose
  their username on that first join (v0.0.12).
- The command-line tool (`npm run admin`) works against the live database from the developer's
  computer (section 9, step 8): invites, players, revoke, reissue a pass.
- A **minimal protected admin endpoint** on the server (`/admin`, requires `ADMIN_KEY`), for what
  the command line can't do on a running server: list sessions and connected players with ping,
  kick a player, end a session with notice, free a desk stuck in the wrong state.
- Every admin action is logged. The complete admin dashboard is **v0.0.27**.

---

## 3. Backups

**Priority:** Critical

- A small scheduled job in the same Railway project runs `pg_dump` **every day**, compresses it and
  uploads it to a Cloudflare R2 bucket.
- Copies are kept for **14 days** (at least the plan's seven), older ones deleted by the job.
- `npm run db:restore -- <file>` restores a backup into a database (a fresh one for a drill, or the
  live one in an emergency), with a confirmation prompt.
- **Restore drill:** before this version is done, a backup is restored into a fresh database, the
  server is pointed at it, and a player's base and paper are checked to be intact. The result is
  recorded in the guide.

---

## 4. Logs and Monitoring

**Priority:** High

- The structured logs from v0.0.13 go to Railway's log viewer (searchable by session id and player
  id), and are kept for the alpha period.
- A free external uptime check (for example UptimeRobot) calls `/health` every few minutes and
  emails the developer if the server is down.
- Errors are logged with context; the same error repeating is logged once with a count.

---

## 5. Playtest Feedback Log

**Priority:** High

- Opened with **F8** or from the pause menu.
- Category: bug, gameplay frustration, confusing interface, performance problem, balance concern,
  missing feature, general enjoyment. Free text, optional steps to reproduce, an enjoyment rating
  (1 to 5).
- Attached automatically: version, player and session, position and mode, recent ping and frame
  rate, device and browser.
- Stored in the `feedback` table, rate limited, and exported as CSV or Markdown with
  `npm run admin -- feedback export`.

---

## 6. Testing at Scale

**Priority:** Critical

- Bots join and leave at random, drop their connection, and keep playing through a server restart
  (a graceful one and a killed process), never duplicating a base or a reward.
- The load test runs against a Railway deployment with saving on: two sessions of 16 bots.
- Measured and recorded in the README: server tick stability, database writes per second and their
  latency, reconnection time after a refresh and after a restart, server memory over a multi-hour
  run, and the monthly cost observed.

---

## 7. The First Online Playtest

**Priority:** Critical

Played on the deployed server, from two computers on two different networks (v0.0.10's mandatory
acceptance sequence, adapted to sessions and portable bases):

1. The developer joins a session and is placed on a desk.
2. The friend joins the same session and is placed on another desk.
3. Both build aircraft and buildings.
4. Both complete missions and earn paper.
5. Both fight in the air.
6. One player disconnects; the other keeps playing.
7. The disconnected player returns within the grace and is back on the same desk.
8. A raid is started on a player who then leaves: the raid finishes normally, then the desk empties.
9. Both leave.
10. The server is restarted (and, separately, the process is killed).
11. Both return in a new session, on new desks, with their bases, planes and paper as they left them.

Also in this playtest (left over from v0.0.11, they need real hardware):

- The controller checklist on a real Xbox or PlayStation controller.
- The performance budgets measured with `?perf` on both test computers.
- The second two-player playtest's blocking issues fixed.

The result, the date, the builds used and any deviations are recorded in the README.

## 9. Setup Guide for the Developer

The guide is **[docs/SERVER_SETUP.md](../SERVER_SETUP.md)**: nine steps (the Railway project and
server, the database, two secrets, the server's settings and address, pointing the game at it,
backups and the restore drill, the uptime check, invites, an optional domain), then how to run it
(logs, admin tools, the feedback log, restoring, the load test) and what to check when something
goes wrong. Each step says what to click or type. It was checked against Railway's, Vercel's,
Cloudflare's and UptimeRobot's documentation on 2026-11-05 and is updated whenever the developer
finds a step that doesn't match.
