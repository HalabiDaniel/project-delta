# paperwars.io: Version 0.0.10 Development Plan

**Development stage:** Private two-player alpha (infrastructure)
**Release type:** Major persistence, deployment and stability milestone
**Release theme:** Persistent Multiplayer, Server Recovery and the First Externally Reachable Alpha
**Builds on:** [v0.0.9](../MULTIPLAYER.md) (core multiplayer)
**Followed by:** [v0.0.11](v0.0.11.md) (complete art integration and controller support)

Part of the [roadmap to v0.1.0](README.md).

---

## Overview

Version 0.0.9 introduced the first multiplayer architecture: an authoritative Node and Colyseus
server (`server/WorldRoom.ts`, `server/world/ServerWorld.ts`) that runs the single-player rule
classes for every player, shared sessions of up to eight players (`NET.maxPlayers` in
`src/net/protocol.ts`), territory claiming, synchronised flight with client prediction and
interpolation, player-versus-player combat with kill and assist credit, raids on player bases
under the fairness rules in `PVP` (`src/config.ts`), rival missions, emotes, and reconnection
within a 60-second grace period (`NET.reconnectGrace`).

Version 0.0.9 is, however, a session that lives only in memory. Its own known limitations say so:
there are no accounts, no persistence and no campaign, and a server restart ends every session.
A player who closes the browser for longer than the grace period loses their territory, their
paper, their buildings and their planes.

Version 0.0.10 turns that session into a world that remembers. It is the first half of the
original 0.1.0 plan: everything needed for the developer and one invited friend to play together
from separate computers and networks, leave, and return later to the same world. The second half,
complete art integration and controller support, follows in v0.0.11 and is tested on top of the
infrastructure built here.

The release has five central objectives:

1. Give every player a stable, secure identity that survives browser restarts and reconnects.
2. Persist the world (territories, buildings, resources, aircraft and progression) in PostgreSQL,
   with transactions that cannot duplicate rewards.
3. Make the server survive restarts, crashes and incomplete writes without losing legitimate
   progress.
4. Protect offline players and keep the existing fairness rules intact across disconnects.
5. Deploy a private, invite-only alpha that two people can reach over HTTPS and secure WebSockets.

The release must preserve the existing PlayCanvas, TypeScript and Colyseus architecture. Do not
migrate to another game engine, network framework or language. Do not introduce new gameplay
systems, a new visual direction, or the HUD, audio and menu redesigns planned for later versions.

The overriding priority is a reliable persistent world rather than new features.

## 1. Persistent Player Identity

**Priority:** Critical
**Goal:** Recognise the same player after a refresh, a closed browser, a new day or a server
restart, without a public registration system.

### A. Identity model

- Every player has a stable, server-issued player ID (UUID) that owns their territory, resources,
  aircraft and records.
- The display name (today stored in `localStorage` by `src/mp/Lobby.ts` and cleaned by
  `cleanName` on the server) remains a changeable label only. It must never decide ownership.
- The Colyseus `sessionId` is a connection identifier, not a player identifier. `ServerWorld`
  pilots must be keyed by player ID, with the session ID mapped to it on join.

### B. Private-alpha authentication

- On first join with a valid invite (see section 7), the server issues a long random device token
  (at least 128 bits of entropy).
- The client stores the token locally and presents it in `onAuth` (`server/WorldRoom.ts`), which
  today only checks the protocol version.
- The server stores only a hash of the token (for example SHA-256 with a server-side pepper), never
  the token itself.
- Tokens can be revoked by the developer. A revoked or unknown token cannot join.
- A player can move to another computer by using a one-time transfer code generated from the
  pause menu or by the developer.
- No passwords, email addresses or third-party sign-in yet. Public accounts belong to v0.0.19.

### C. Impersonation and duplicate connections

- The server never trusts a client-supplied player ID. The player ID is derived from the verified
  token.
- If the same player connects twice, the newer connection takes over and the older one is closed
  with a clear message ("Opened in another tab").
- Changing the display name in the client cannot take over another player's territory, kills,
  bounties or records.

## 2. Database Architecture

**Priority:** Critical
**Goal:** Introduce PostgreSQL as durable storage for gameplay-critical state, with a schema that
can evolve safely.

### A. Technology

- PostgreSQL (version 15 or later) accessed from the existing Node server.
- A small, typed data-access layer (for example `server/db/`) with parameterised queries only.
- Connection pooling, connection timeouts and automatic reconnect on database loss.
- A local development setup (Docker Compose or a documented local install) and a test database
  for automated tests.

### B. Schema (initial)

| Table | Contents |
|---|---|
| `players` | Player ID, display name, token hash, created and last-seen times, revoked flag |
| `worlds` | World ID, name, created time, save-format version, settings |
| `territories` | World, territory ID (T1 to T9), owner player ID, claimed time, protection state |
| `buildings` | Territory, slot, kind (`turret`, `launcher`, `radar`, `workshop`, `storage`), level, health |
| `balances` | Player, world, paper (and later resources), stored and protected amounts, production timestamp |
| `aircraft` | Player, plane type, status (ready, airborne, damaged, destroyed), health, saved loadout |
| `transactions` | Idempotency key, player, kind, amount, reason, mission or event reference, time |
| `missions` | Player, mission template, state, offered and resolved times, outcome, reward |
| `progress` | Player, tutorial flags, statistics, unlocks |
| `pvp_records` | Raid history, cooldowns, shields, kill windows (the state behind `PVP` rules) |
| `feedback` | Structured playtest feedback (see section 8) |
| `schema_migrations` | Applied migration versions |

The exact schema is the agent's decision, but every row must have a clear owner and every
balance change must be explainable from the transaction log.

### C. Migrations and versioning

- Versioned migration files in the repository, applied automatically on server start.
- A save-format version per world. The server refuses to load a world written by a newer version
  and explains why in the log and to connecting clients.
- Older formats are upgraded by migrations, never by ad hoc code paths.

## 3. Persistent Territories, Economy, Aircraft and Progression

**Priority:** Critical
**Goal:** A returning player finds their world exactly as the rules say it should be.

### A. Territories and bases

Persist:

- Territory ownership and territory identifiers.
- Constructed buildings, their slots, levels and health (the state managed by `src/base/Base.ts`).
- Damage from raids, which stays until repaired (as in v0.0.7).
- Defensive installations and their configuration.
- Production state and storage capacity.

On reconnect, the player returns to their existing territory with their base intact, without going
through the claim flow again.

### B. Economy

- Persist balances: paper, capacity and the protected reserve (`ResourceManager`, `Ledger`,
  `HomeIncome` in `src/systems/`).
- Offline production is credited on return from the elapsed time, using the same production and
  storage rules as online play. It is capped by storage and never exceeds what the player could
  have earned online.
- Every change is a row in `transactions` with an idempotency key built from its cause (mission
  ID, raid ID, kill event ID, build request ID).
- The same key applied twice has no effect. This prevents duplicated rewards from repeated
  network messages, browser refreshes, reconnects, server restarts and retried completion requests.
- Balance updates and their transaction row are written in one database transaction.

### C. Aircraft

Persist:

- Owned and recovered aircraft, type, health and repair status.
- Saved loadouts and the quick-rebuild selection.
- Availability (ready, in repair, destroyed).
- Customisation fields as empty placeholders, so v0.0.18 does not need a breaking migration.

The free emergency Dart remains free and is never stored as an asset that can be accumulated.

### D. Interrupted sorties

Airborne aircraft need explicit, documented rules. Proposed defaults, to be confirmed by the
developer:

| Situation | Result |
|---|---|
| Disconnect, reconnect within the grace period | The sortie resumes where the server kept it (current v0.0.9 behaviour) |
| Disconnect longer than the grace period, plane not in combat | The plane glides home and is returned undamaged; the mission fails without penalty beyond the lost reward |
| Disconnect longer than the grace period during combat or a raid | The plane is treated as lost, as if shot down, but grants no kill reward to anyone |
| Server restart while airborne | The plane is returned to the hangar in its last saved condition; active missions are cancelled and their stake refunded |

A destroyed aircraft can never be restored. An aircraft is never placed in an invalid position or
duplicated.

### E. Missions and progression

Persist:

- Mission history and outcomes.
- The current mission board, so a refresh does not reroll it.
- Statistics (sorties, kills, raids, defenses), already counted per pilot in multiplayer.
- Tutorial and first-time-tip completion.
- Earned rewards and progression unlocks.

Interrupted missions follow the rules in D: they either resume within the grace period or end in
a defined safe state. They never complete twice.

## 4. Persistent World Lifecycle and Server Recovery

**Priority:** Critical
**Goal:** The world outlives every connection and every server process.

### A. World lifecycle

- At least one persistent private world.
- The world does not reset when all players disconnect. The Colyseus room may be disposed when
  empty, but its state is restored from the database when the next player joins.
- AI territory state (the centre `PVP.centre` and wrecked installations) can be regenerated
  rather than persisted where that is simpler, as long as players cannot exploit it.
- The GDD's seven-day campaign resets are not implemented. They belong to v0.0.19.

### B. Saving

- Critical changes (balances, purchases, builds, raid results, mission outcomes) are written
  transactionally when they happen.
- Less critical state (building health between hits, production timestamps) is saved
  periodically, at most every few seconds, and on shutdown.

### C. Recovery

- Graceful shutdown on `SIGTERM` and `SIGINT`: stop accepting joins, finish in-flight
  transactions, save, then exit. `server/index.ts` already calls `gracefullyShutdown` in tests.
- Startup restoration: load the world, apply migrations, rebuild `ServerWorld` from stored state.
- Recovery from incomplete writes: anything not committed in a transaction is discarded, so the
  world is always in a consistent last-committed state.
- Error logging with timestamps, player IDs and request context.
- A crashed process restarted by the process manager must come back without manual steps.

## 5. Offline Protection and Fairness Across Disconnects

**Priority:** Critical
**Goal:** No player is economically destroyed simply because they were offline.

### A. Offline protection rules (initial alpha values)

- Offline territories cannot be the target of new player-initiated raids. Raid cards against them
  are not offered.
- A raid already in progress when the defender disconnects continues, but losses stay capped by
  the existing rules.
- A reconnect grace period after returning (for example two minutes) during which the player
  cannot be raided while they get their bearings.
- The protected paper reserve and the starter resources are never lost.
- Existing values in `PVP` remain: new-player protection, raid shield, pair cooldown, decaying
  repeat rewards and kill-farming windows.

### B. Persistence of fairness state

- Shields, cooldowns, farm windows and kill windows must be persisted. A server restart must not
  reset them and open a farming window.
- Offline production must not create passive reward farming. Production is capped by storage and
  does not pay defensive rewards.

### C. Documentation

- Every protection rule and its value is listed in the README and tunable in `src/config.ts`.

## 6. Multiplayer Hardening and Server Authority

**Priority:** Critical
**Goal:** Keep the server authoritative and robust against unreliable networks and bad input.

### A. Network reliability

Handle:

- Latency and packet loss (already simulated with `LATENCY` in v0.0.9; extend to loss).
- Temporary connection interruptions and sudden disconnects.
- Browser refreshes, which should resume the same player with the stored token.
- Server process restarts, after which clients reconnect automatically and show a short
  "Reconnecting" state.
- Invalid or malformed messages, which are dropped and logged.
- Duplicate connections (section 1C).
- Full sessions, with a clear "World full" message.

### B. Server authority

The server alone decides resource awards, mission success, territory claims, weapon damage,
construction and repairs. The client never reports outcomes, only inputs and requests.

### C. Data protection

- Secrets (database URL, token pepper, invite codes, admin key) live in environment variables,
  never in the repository or the client bundle.
- Rate limiting on joins, commands and feedback submissions per player and per IP address.
- Validation of every command's shape and range.

### D. Error handling

Provide understandable errors for:

- Failed connections and unavailable servers.
- Session capacity.
- Failed authentication or revoked access.
- Save restoration problems and incompatible versions.

### E. Recovery for players

A player can always recover from routine failures without losing legitimate progress or becoming
permanently unable to play (for example a lost token can be reissued by the developer, and the
territory reassigned).

## 7. Deployment and Private Alpha Access

**Priority:** Very high
**Goal:** The developer and one invited friend can play from separate computers and networks
without running anything locally.

### A. Deployment

- An externally reachable environment for the client and the server. The choice of host is the
  developer's, but it must support WebSockets and a managed or self-hosted PostgreSQL.
- HTTPS for the client and secure WebSockets (`wss://`) for the server.
- A process manager (systemd, PM2, a container platform or equivalent) with automatic restart.
- Configuration through environment variables (`PORT`, `DATABASE_URL`, secrets, allowed origins).
- Basic operational logging, retained for at least the alpha period.
- The client finds the production server without query parameters (today `?mp&server=...`).

### B. Invite-only access

- A simple invite code or invite link is required for the first join.
- The developer can create and revoke invites.
- No public registration.

### C. Room and world administration

The developer can:

- Create or configure the private world.
- Invite the second player.
- Rejoin the existing world.
- See connected players, their territories and connection quality.
- Kick a player, free a territory and reissue a token.
- Recover from common room errors (stuck room, orphaned territory).

A command-line admin tool or a protected admin endpoint is sufficient. `server/index.ts` already
exposes a room listing that can be extended and protected.

### D. Backups

- Daily automatic database backups, kept for at least seven days.
- A documented and tested restore procedure.

## 8. Playtest Feedback Log

**Priority:** High
**Goal:** Collect structured feedback from the first two-player sessions.

### A. Feedback entry

- Opened from the pause menu (and a key such as F8).
- Category: bug, gameplay frustration, confusing interface, performance problem, balance concern,
  missing feature, general enjoyment.
- Free text, optional reproduction steps, and an enjoyment rating.
- Automatically attached context: version, player ID, world, position, current mode, recent
  network quality and frame rate.

### B. Storage and review

- Stored in the `feedback` table, rate limited.
- The developer can export it as CSV or Markdown.
- No analytics platform. Analytics belong to v0.0.19.

## 9. Testing and Verification

**Priority:** Critical

### A. Automated tests

- All existing tests continue to pass (the single-player suites and the v0.0.9 multiplayer tests
  in `server/room.test.ts`, `server/world/world.test.ts` and
  `server/world/prediction.test.ts`).
- New tests against a test database for: token issue and verification, impersonation attempts,
  duplicate connections, transaction idempotency, offline production, interrupted sorties, restart
  restoration, migrations and incompatible save versions.
- Concurrency tests: two players finishing missions at the same moment, a building repaired while
  under attack, an aircraft destroyed during mission completion, an owner reconnecting while their
  balance changes.
- Bots (`server/bots/`) extended to disconnect and reconnect at random, and to survive a server
  restart.
- The load test (`server/loadtest.ts`) repeated with persistence enabled, reporting database
  write rates and latency.

### B. Mandatory acceptance sequence

This sequence must pass on the deployed server, from two computers on two different networks:

1. The developer joins the world and claims a territory.
2. The friend joins and claims a different territory.
3. Both players construct aircraft and buildings.
4. Both complete missions and earn resources.
5. Both engage in aerial combat.
6. One player disconnects.
7. The other continues playing.
8. The disconnected player returns.
9. Both disconnect.
10. The server restarts.
11. Both players return and recover their expected persistent progress.

The result is recorded in the README with the date, the builds used and any deviations.

### C. Additional checks

- Browser refresh and full browser closure.
- Disconnect during flight and during combat.
- A killed server process (not a graceful stop) followed by automatic restart.
- A database restore from backup into a fresh environment.

### D. Measurements

- Server tick stability with persistence enabled.
- Database write latency and writes per second.
- Reconnection time after a refresh and after a server restart.
- Memory use of the server over a multi-hour session.

## 11. Developer Responsibilities

The developer is responsible for:

- Choosing and paying for hosting and a PostgreSQL provider, and creating the accounts.
- Owning a domain or subdomain for HTTPS, if one is wanted.
- Supplying production secrets through the hosting provider's environment settings.
- Confirming the interrupted-sortie and offline-protection rules (sections 3D and 5A).
- Inviting the friend and scheduling playtests.
- Running the acceptance sequence together with the friend.
- Reviewing the feedback log and approving the release.

## 12. AI Agent Implementation Strategy

**Priority:** Critical

The AI coding agent performs the technical implementation, testing, integration and
documentation.

| Phase | Focus |
|---|---|
| 1 | Audit v0.0.9: list everything kept only in memory, establish a regression baseline |
| 2 | Player identity: tokens, `onAuth`, player IDs in `ServerWorld`, duplicate connections |
| 3 | Database: schema, migrations, data-access layer, local and test databases |
| 4 | Persist territories, buildings, balances and the transaction log with idempotency |
| 5 | Persist aircraft, missions, progression and fairness state; interrupted-sortie rules |
| 6 | World lifecycle, periodic saving, graceful shutdown, startup restoration, crash recovery |
| 7 | Offline protection, reconnect grace, hardening, rate limits, error messages |
| 8 | Deployment, invite access, admin tool, backups, feedback log |
| 9 | Automated tests, bots with disconnects and restarts, load test with persistence |
| 10 | Developer-and-friend acceptance sequence and release-blocking fixes |

Rules:

- Work in reviewable increments, one phase per pull request where practical.
- Do not mark a phase complete because the code compiles. Verify behaviour through automated
  tests, browser tests and real gameplay.
- Preserve every working feature from earlier versions, single-player included.
- Stop at developer checkpoints after phases 3, 6 and 8 for review.

## 13. Definition of Done

- [ ] Every player has a persistent, secure identity that does not depend on the display name.
- [ ] Tokens are stored hashed and can be revoked and reissued.
- [ ] Territory ownership, buildings, levels and health persist.
- [ ] Balances persist and every change is in the transaction log.
- [ ] No reward can be duplicated by retries, refreshes, reconnects or restarts.
- [ ] Offline production follows the online rules and storage caps.
- [ ] Aircraft, loadouts and availability persist; destroyed aircraft cannot return.
- [ ] Interrupted sorties follow the documented rules.
- [ ] Mission history, statistics and tutorial progress persist.
- [ ] Shields, cooldowns and farming windows survive a restart.
- [ ] The world survives all players leaving and a server restart.
- [ ] Graceful shutdown, startup restoration and crash recovery work.
- [ ] Incompatible save versions are refused with a clear message.
- [ ] Offline players are protected from new raids.
- [ ] The server is reachable over HTTPS and WSS from outside the developer's network.
- [ ] Access is invite-only, and the developer can administer the world.
- [ ] Daily backups run and a restore has been tested.
- [ ] The feedback log works and can be exported.
- [ ] All existing tests and the new persistence and concurrency tests pass.
- [ ] The mandatory acceptance sequence has passed with the developer and the friend.
- [ ] Deployment, backup and restore procedures are documented.

## Final Design Principle

Version 0.0.10 is the moment paperwars.io stops forgetting. Two players should be able to claim
their desks, build, fight, close their browsers and come back the next day to a classroom that
remembers exactly what they earned and lost, and nothing more. Every later version builds on this
world, so it must be trustworthy before it is beautiful.
