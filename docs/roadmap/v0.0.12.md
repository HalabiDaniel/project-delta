# paperwars.io: Version 0.0.12 Development Plan

**Development stage:** Private Playable Alpha
**Release type:** Interface overhaul
**Release theme:** HUD and UI Revamp: one paper-and-pencil design system, controller-first navigation, readable at a glance
**Builds on:** [v0.0.11](v0.0.11.md) (art integration and controller support)
**Followed by:** [v0.0.13](v0.0.13.md) (audio and music revamp)

Part of the [roadmap to v0.1.0](README.md).

---

## Overview

Version 0.0.7 redesigned the HUD around fixed zones, icon-and-number values, short phrases and first-time tips (GDD §15). Version 0.0.8 gave the world its permanent look: pencil outlines, paper materials and soft cartoon light. Version 0.0.9 added the multiplayer HUD (scoreboard, kill feed, raid alerts, emotes), largely as additions in `src/mp/MpHud.ts`, `src/mp/MpViews.ts` and `src/mp/mp.css` alongside the single-player HUD. Version 0.0.10 made the world persistent and playable by two people over the internet. Version 0.0.11 completed the 3D assets and added controller support, including controller navigation for every existing menu.

The interface now works, but it shows its history. It was built feature by feature: tokens live in `src/ui/hud.css`, multiplayer screens use a parallel stylesheet, components are reimplemented per screen, controller focus was added to existing markup rather than designed into it, and the layout was tuned for one screen size. It does not yet match the finished sketchbook world from v0.0.11.

Version 0.0.12 rebuilds the in-game HUD and every management interface on one consistent, responsive design system that matches the art direction and treats the controller as a first-class input.

The release has five central objectives:

1. Establish a single paper-and-pencil UI design system: tokens, components and rules that every screen uses.
2. Make every screen fully navigable by controller, keyboard and mouse, designed around focus rather than hover.
3. Rebuild the flight HUD, the management screens and the multiplayer HUD on that system.
4. Make the interface responsive from 1080p to 4K and ultrawide, and accessible (colour-blind safe, scalable, reduced motion, subtitles).
5. Make all interface text localisation-ready.

Preserve:

- The PlayCanvas, TypeScript and browser-based architecture. The HUD remains DOM over the canvas; do not move to a different engine or a canvas-rendered UI.
- The Node and Colyseus multiplayer server and its authoritative rules. The UI revamp changes presentation, not gameplay.
- The GDD §15 principles: icon plus number, one to three words, show what matters now, details on demand, colour and shape together.
- Every existing feature and its tests.

Do not expand scope. Main menu, lobby, settings screens, loading screens and branding belong to v0.0.14. Audio belongs to v0.0.13.

## 1. UI Design System

**Priority:** Critical
**Goal:** One documented set of tokens and components from which every screen in the game is built.

### A. Design tokens

Consolidate and extend the tokens currently declared in `src/ui/hud.css` (`--paper`, `--ink`, `--friend`, `--hostile`, `--warn`, `--good`, `--off`, the threat and lock colours, radii `--r`, spacing `--s1`..`--s4`, type sizes `--t-*`) into one token source used by both single-player and multiplayer UI.

Token groups:

| Group | Contents |
|---|---|
| Colour: surfaces | Card stock, card stock solid, recessed paper, edge, shadow |
| Colour: ink | Primary, secondary, tertiary ink |
| Colour: meaning | Friendly, hostile, warning, good, off, objective (orange), neutral (grey) |
| Colour: status | Threat levels 1-3, tracking, locking, firing, medal tiers |
| Spacing | A 4 px based scale |
| Radius | Card, small, pill |
| Type | One bold tabular face for numbers, one plain face for words, three sizes plus a display size |
| Elevation | Flat, raised, floating (tooltips, alerts) |
| Motion | Durations and easing for fold-in, pop, fade; all zeroed by reduced motion |
| Focus | Focus ring colour, width, offset |

Requirements:

- One source of truth (CSS custom properties generated from or mirrored by a TypeScript token module) so code that draws on the canvas (world labels, markers, the mini-map) uses the same colours.
- Ownership colours must match the art direction's blue player, red hostile, grey neutral, orange objective.
- A colour-blind palette is a token swap, not a separate stylesheet.
- Retire `src/mp/mp.css` as a separate visual language; multiplayer UI uses the shared tokens.

### B. Components

Build a small shared component set (TypeScript functions or classes producing DOM, consistent with the existing `src/ui/dom.ts` and `src/ui/icons.ts` approach). Do not introduce a framework unless the gain is clear and documented.

| Component | Purpose |
|---|---|
| Card | Cut card stock with folded corner and soft shadow; the container for every panel |
| Chip / tag | Small labelled value or state (bonus, record, status) |
| Button | Label plus a key cap or controller glyph showing its binding; primary, secondary, danger |
| Icon button | Icon-only action with tooltip and accessible name |
| Bar | Health, range, boost, progress, capacity; with thresholds |
| Stat | Icon plus tabular number, optional delta pop |
| Pips | Discrete counts (bombs, levels, ratings) |
| Tooltip | Details on demand; opened by hover, focus or a controller info button |
| Alert | Short top-centre message with severity; at most three visible |
| Focus ring | Visible, high-contrast, consistent across every focusable element |
| List / grid | Focus-navigable collections (plane cards, mission cards, slots) |
| Tabs | Section switching in management screens |
| Dialog | Confirmations (remove building, end sortie, leave world) |
| Glyph | Input glyph for keyboard, Xbox-style or PlayStation-style controller |

Requirements:

- Each component documents its states: default, hover, focused, pressed, disabled, warning, critical.
- Each component works with controller, keyboard and mouse.
- Each component has an accessible name and role.
- Components scale with the HUD size setting and with text scaling.

### C. Visual language

- Panels look like cut card stock and paper, consistent with the v0.0.8 and v0.0.11 world: grain, folded corner, soft shadow, pencil-like strokes for dividers.
- One line-icon family, extended from `src/ui/icons.ts`, drawn to match the pencil style. Every new icon has a name in `ICON_NAMES` for its tooltip.
- Motion is short and functional: panels fold in, deltas pop and fade, alerts slide. No looping decorative motion on the HUD.
- The centre of the screen stays clear during flight.

### D. Documentation

- A design system reference in `docs/` describing tokens, components, states and usage rules, with screenshots.
- A developer gallery page (for example `?ui-gallery`) rendering every component in every state, at every HUD size, in both palettes, with keyboard and controller glyphs.

## 2. Focus-First Navigation

**Priority:** Critical
**Goal:** Every screen is designed around a focus model, so controller, keyboard and mouse are equal.

### A. Focus model

- One focus manager for the whole UI, built on the unified input-action layer from v0.0.11.
- Directional navigation (D-pad, left stick, arrow keys) moves focus spatially between focusable elements, with explicit overrides where geometry misleads.
- Confirm and back (A / Cross, B / Circle, Enter, Escape) behave the same on every screen.
- Shoulder buttons or Q/E switch tabs; triggers or page keys scroll long lists.
- Focus is never lost: opening a panel focuses its first sensible element; closing it returns focus to the element that opened it.
- Focus is never trapped except in modal dialogs.

### B. No hover-only interactions

- Everything available on hover is also available on focus, and through an info button (Y / Triangle) on controller.
- Tooltips open on focus after a short delay and close on move.
- Drag interactions, if any, have a button-based alternative.

### C. Flight versus menu input

- While flying, gameplay owns the stick and buttons; the HUD is not focusable.
- Opening a menu (pause, base management, logbook) switches the input context cleanly with no stray inputs passed to the plane.
- Quick actions during flight (emotes, mini-map zoom) use a dedicated radial or button layer, not focus navigation.

## 3. Flight HUD

**Priority:** Critical
**Goal:** Rebuild the flight HUD on the design system, keeping the fixed zones and adding nothing the player does not need.

### A. Zones

Keep the GDD §15.3 zone model, rebuilt with the new components:

| Zone | Flying |
|---|---|
| Top left | Paper (and other resources when v0.0.15 adds them), production, storage |
| Top centre | Objective, threat panel, raid alert, alerts, tips |
| Top right | Mini-map |
| Bottom left | Health, range |
| Bottom centre | Speed, altitude, boost; landing checks |
| Bottom right | Ink, bombs (pips), secondary weapon |

### B. Elements

Rebuild, from `src/ui/AirHud.ts`, `PlaneHud.ts`, `ThreatHud.ts`, `MiniMap.ts`, `WorldLabels.ts` and `Alerts.ts`:

- Health and range bars with clear critical thresholds.
- Speed, altitude and boost.
- Ink as a number, bombs as pips.
- Current objective with distance, progress and clock.
- Threat panel and threat ring, rocket lock warning.
- Aircraft markers with an icon for what each is doing, ownership colour and shape.
- Mission markers and target indicators consistent with the outline style.
- At most three alerts at once, with priority ordering.

### C. Combat de-emphasis

- In a fight, less urgent panels step back (lower opacity, smaller) and return afterwards.
- Critical warnings (low health, lock, raid on home) always win.

### D. Extensibility

- Resource displays must accept additional resources (ink and rubber balls arrive in v0.0.15) without layout changes.
- Escort status (v0.0.16) must fit into an existing zone without redesign.

## 4. Management Screens

**Priority:** Critical
**Goal:** Rebuild every non-flight screen on the design system with full focus navigation.

### A. Screens in scope

| Screen | Current source | Requirements |
|---|---|---|
| Garage / aircraft selection | `src/ui/Garage.ts` | Plane cards with price and mission fit; inspector with ratings as pips and loadout as numbers; fold and launch |
| Mission board | `src/ui/MissionPanel.ts` | Safe, balanced and high-risk cards; rival cards in multiplayer; swaps; reward and risk at a glance |
| Base management | `src/ui/BaseHud.ts`, `src/base/BaseMode.ts` | Slot markers, build tray, slot inspector, upgrade, repair, remove, missing-resource display |
| Repair and rearm | `src/ui/BaseHud.ts`, `src/ui/Garage.ts` | Repair all, per-building repair, rearm, costs |
| Mission results / battle report | `src/ui/ReportCard.ts` | Headline and medal, four big numbers, chips, Details breakdown; defense report for raids |
| Logbook | `src/ui/Logbook.ts` | History, records, medals, filters |
| Pause menu | `src/ui/Menus.ts` | Resume, settings entry, leave; full settings arrive in v0.0.14 |
| Economy strip | `src/ui/EconomyStrip.ts` | Resources, production, capacity, protected amount |

### B. Requirements

- Each screen keeps its current functionality.
- Each screen is reachable and fully usable by controller only.
- Costs show what is missing, not just the total.
- Destructive actions (remove building, end sortie, leave world) use a confirm dialog.
- Screens open and close in under 150 ms of UI work.

## 5. Multiplayer HUD

**Priority:** Very high
**Goal:** Bring the multiplayer interface into the same design system and make other players' presence clear.

### A. Elements

Rebuild from `src/mp/MpHud.ts` and `src/mp/MpViews.ts`:

- Scoreboard: players, territory, kills, assists, score, connection state, ping.
- Kill feed: short, icon-led, ownership coloured, readable at speed.
- Raid alerts: incoming raid on your base, with attacker, ETA where known, and a one-press interception card.
- Presence: online, away, offline and protected states for every player and territory, on the mini-map and scoreboard.
- Emote wheel or bar, controller-friendly.
- Rival mission cards that look like the single-player mission cards.

### B. Requirements

- Multiplayer and single-player screens are visually indistinguishable in style.
- Connection problems (reconnecting, server lost) appear as standard alerts and dialogs from the design system; full error screens are v0.0.14.

## 6. Device-Aware Hints

**Priority:** Very high
**Goal:** Every hint shows the binding for the device the player is using right now.

### A. Glyph sets

- Keyboard and mouse.
- Xbox-style controller.
- PlayStation-style controller.
- Generic controller fallback.

### B. Behaviour

- The last-used device decides which glyphs are shown, switching live without reload.
- Hints read bindings from the input-action layer, so rebinding (v0.0.14) updates them automatically.
- Key hints keep the v0.0.7 behaviour: shown for the first sorties, then on H (or the controller equivalent) or by setting.
- First-time tips appear once per player, next to what they explain, and are stored with the persistent player profile from v0.0.10.

## 7. Responsive Layout

**Priority:** Very high
**Goal:** The interface looks right on every desktop screen the alpha will meet.

### A. Targets

| Resolution | Aspect | Requirement |
|---|---|---|
| 1280 x 720 | 16:9 | Usable, nothing overlaps |
| 1920 x 1080 | 16:9 | Reference layout |
| 2560 x 1440 | 16:9 | Sharp, proportionate |
| 3840 x 2160 | 16:9 | Sharp, proportionate, no tiny text |
| 2560 x 1080 / 3440 x 1440 | 21:9 | Zones stay in a comfortable reading area |
| 1920 x 1200 | 16:10 | No clipping |

### B. Requirements

- Zones anchor to their corners and scale from them, as today.
- The HUD size setting (S / M / L) remains and combines with resolution scaling.
- Ultrawide screens can keep the HUD inside a 16:9 safe area (setting).
- Icons are vectors; no blurry raster UI at 4K.
- Browser zoom and device pixel ratio are handled.

## 8. Accessibility

**Priority:** High
**Goal:** The interface is usable by players with common visual, motion and hearing needs.

### A. Colour

- A colour-blind safe palette option, tested for protanopia, deuteranopia and tritanopia.
- State is never shown by colour alone: icons, pips, shapes and labels accompany colour everywhere, including world markers.

### B. Scale and contrast

- Text scaling independent of HUD size.
- Minimum contrast ratios on card stock for text and icons.
- An optional higher-contrast panel background.

### C. Motion

- A reduced motion setting that removes fold-in, pop and slide animations and camera-shake-driven UI motion.

### D. Hearing

- Subtitles or visual indicators for important sounds: rocket lock, raid incoming, bandit, being hit, defenses spotting you. The current sound set in `src/ui/Sounds.ts` (`spotted`, `lock`, `launch`, `hit`, `bandit`, `raid`, and so on) defines the minimum list.
- v0.0.13 extends these indicators to its new audio cues.

---

## 9. Localisation-Ready Text

**Priority:** Medium
**Goal:** All interface text can be translated later without code changes.

### A. Requirements

- Every string comes from the dictionary (extending `SAY` and friends in `src/ui/strings.ts`); no literal text in components.
- Strings are keyed, with an English base file.
- Numbers, times and distances go through formatting functions (extending `src/ui/format.ts`).
- Layout tolerates text up to 40 per cent longer than English.
- No text baked into images or icons.
- A pseudo-localisation mode (accented, lengthened text) for testing.

Actual translations are not part of this version.

---

## 10. Testing and Verification

**Priority:** Critical

### A. Automated

- Unit tests for the focus manager: directional moves, focus restore, modal trapping.
- Unit tests for glyph selection and live device switching.
- Snapshot or DOM tests for each component in each state.
- A check that no component contains literal user-facing text.
- Existing tests continue to pass.

### B. Browser

- Screenshots of every screen at 1080p, 1440p, 4K and 21:9, at each HUD size, in both palettes, captured in headless Chromium and committed as a checkpoint.
- Pseudo-localisation screenshots for every screen.

### C. Hands-on

- Controller-only walkthrough: lobby, claim, garage, launch, fly, fight, land, base management, repair, mission results, logbook, pause, leave.
- Keyboard-only walkthrough of the same.
- Mouse walkthrough of the same.
- Two-player session with one controller player and one keyboard player.
- Colour-blind simulation check of flight HUD and markers.

### D. Performance

- HUD update cost per frame measured before and after; no regression in frame time.
- No layout thrashing during flight.

## 13. AI Agent Implementation Strategy

**Priority:** Critical

| Phase | Focus |
|---|---|
| 1 | Audit the current UI: every screen, component, token and string; record a screenshot baseline |
| 2 | Tokens, components, focus manager and the gallery page; developer checkpoint on the style |
| 3 | Flight HUD rebuild |
| 4 | Management screens rebuild |
| 5 | Multiplayer HUD rebuild; retire the separate multiplayer stylesheet |
| 6 | Device-aware hints and responsive layout |
| 7 | Accessibility and localisation readiness |
| 8 | Testing, screenshots, two-player playtest, fixes; developer checkpoint |

Rules:

- Work in reviewable increments, one phase per pull request where practical.
- Do not mark a phase complete because the code compiles; verify in the browser, with tests, and with controller input.
- Preserve every earlier feature. When a screen is rebuilt, its behaviour stays the same unless this plan says otherwise.
- Stop at the developer checkpoints after phases 2 and 8.

## 14. Definition of Done

- [ ] One token source is used by every screen, single-player and multiplayer.
- [ ] The shared component set exists, is documented and appears in the gallery in every state.
- [ ] No screen uses the old HUD styles or the separate multiplayer stylesheet.
- [ ] The flight HUD is rebuilt in the fixed zones and keeps the centre clear.
- [ ] Garage, mission board, base management, repair, results, logbook, pause and economy strip are rebuilt.
- [ ] Scoreboard, kill feed, raid alerts, presence and emotes are rebuilt.
- [ ] Every screen is fully usable by controller only, keyboard only and mouse.
- [ ] No functionality depends on hover.
- [ ] Hints show the correct glyphs for the active device and switch live.
- [ ] The interface is correct at 720p, 1080p, 1440p, 4K, 16:10 and 21:9 and at each HUD size.
- [ ] The colour-blind palette, text scaling, reduced motion and sound subtitles work.
- [ ] No literal user-facing text remains in components; pseudo-localisation shows no clipping.
- [ ] No frame-time regression from the HUD.
- [ ] All existing tests and the new UI tests pass.
- [ ] The developer has approved the style and completed a two-player session.

---

## Final Design Principle

The interface should feel like part of the sketchbook world: card stock, ink and pencil, read in a glance, reachable from any controller or keyboard. Every later version builds on this system rather than around it, so paperwars.io keeps one clear visual language as it grows.
